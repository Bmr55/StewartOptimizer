# Browser worker execution

The browser UI creates one module worker for each optimization run. The worker owns a headless `Optimizer`; the main thread uses `WorkerOptimizer` to retain selection, JSON/CAD export, and the most recent completed population. Direct imports of the headless `Optimizer` and the root compatibility adapter remain available without a worker.

Every message has a unique `runId`. Main to worker: `start` includes serializable `effectiveSettings()` and `cancel` requests an abort for that ID. Worker reconstruction maps `reference_layout` back to the imported reference option and passes the raw `servoRatings`, condition limit, seed, and other effective options through. Worker to main: `started` acknowledges initialization and carries the budgeted pose work; `progress` contains a bounded summary; `checkpoint` contains one fully evaluated retained population; `result` contains the outcome and final checkpoint; `error` carries a `phase` of `startup` (the optimizer could not be constructed), `runtime` (the run threw after starting) or `overlap` (a second `start` arrived while a run was active in that worker) plus the message, and for `startup` and `runtime` the error name. The adapter ignores mismatched IDs and messages after settlement. The `overlap` error is answered with the new message's `runId` and leaves the active run untouched; a repeated `start` that carries the active run's own `runId` is ignored, and a `cancel` whose `runId` matches no active run (including a missing `runId` while idle) is ignored; the UI also disables Run during an active run. A `start` whose `settings` is not an object with a `requirements` object is answered with a `startup` error instead of running default requirements.

The adapter validates every reply before applying it. A `checkpoint` or `result` population is applied only when it is complete and every candidate has a layout that passes the shared layout check with an id and two finite servo bounds; an invalid candidate, a `result` without an `outcome` object carrying a `status` string, or any exception thrown while handling a reply ends the run as a runtime failure (settled promise, terminated worker, `failed` outcome with the reason, last valid population retained) instead of leaving the UI in Running. A worker factory that returns no worker and a bare `onerror` without a message produce readable startup-failure messages.

Progress contains elapsed milliseconds, completed/total candidates, generation, front size, a compact best-candidate summary from the completed retained population, actual completed pose work, budgeted pose work, and approximate ETA. ETA uses observed elapsed time per completed candidate, remains unavailable until three candidates finish, and remains unavailable when timing is invalid. The budget is a preflight upper bound; actual work can be lower when evaluation exits early. Worker progress publishes at most once per 100 ms and never carries layouts, populations, or workspace samples. The UI applies the same 100 ms cap to direct headless/fallback progress. Checkpoints and final results may carry the completed retained population; they are not published for unfinished generations. Result and runtime-error messages include a final bounded summary so the dashboard shows exact terminal counts even if the last progress tick was throttled. The worker checks for cancellation through the optimizer's existing abort signal and pose-batch yields.

Startup errors and startup timeouts (5 seconds by default, configurable as `startupTimeoutMs` on `WorkerOptimizer`) terminate the worker, display the failure, and enable **Run on main thread**. The fallback starts only after the user selects it and uses the same normalized requirements, seed, bounds, options, budgets, and yielding core. Runtime errors terminate the worker and display any last completed population as partial. A later Run creates a fresh worker.

`npm test` checks deterministic worker/headless equivalence, run IDs, overlap, throttling, checkpoints, cancellation, failure, timeout, fallback, and restart. `npm run test:browser` checks real module-worker completion, cancellation/restart, result export, and blocked-worker fallback in the development server.
